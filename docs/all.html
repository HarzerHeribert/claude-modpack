Lab notes

What we tried while building this modpack, how we measured it, and why most of it did not ship.

The modpack is eight mods for Claude Code. Behind them is a lab where every idea has to show, in graded runs, that it saves something without making the work worse. Most ideas don't make it: a nudge Claude never followed, a gate that reassured falsely, a 10,000-star tool that, installed, saved nothing we could measure. These notes are about those decisions. The data behind every number is in benchmarks/, with the harness to run it again.

Who wrote this. Claude (Opus 5.5) wrote these notes from this repository's results files and commit history; HarzerHeribert reviewed them. We build a competing pack, so read what we say about other tools with that in mind: every claim about them links to their own words, and every number of ours to the runs behind it. If we got something wrong about your project, open an issue and we will correct it here.

#How we measure

The same setup runs through every note unless it says otherwise.

  • The work. Seven tasks on click 8.5.0 (79 files of Python), from a one-line lookup to a feature, later eight with a signature change, plus four tasks on a generated 54-file deployment repository (Kubernetes, Compose, GitHub Actions, Ansible). Every task is graded by a fixed rule: hidden tests for code, a parser for YAML, a term list for explanations. A run that saves money and gets the answer wrong counts as a failure, not a saving.
  • The runs. Headless Claude Code (claude -p), Claude Opus 5.5, one fresh copy of the repository per run. Each condition names exactly which mods load, so nobody's personal settings decide anything. A long session forks a prepared session that has already read all of click's source, src/click (about 220k tokens of context), which is where real work spends most of its time.
  • The cost. Read request by request from the transcripts and priced at list prices: Opus 5.5 at $4 per million input tokens, $20 output, $0.20 for a cache read, $8 for a cache write (Claude Code writes with the one-hour lifetime; a five-minute write is $5). On a subscription these are API-equivalent estimates, not a bill.
  • The uncertainty. Two to eight runs per task and condition. Differences are reported for the average task with 95% bootstrap intervals, resampling runs within each task (Efron & Tibshirani 1993). An interval that crosses zero means not shown, and we say so. Before a confirmation run we wrote down what would count as confirmed (an example).
  • The limits. Mostly one small Python repository and tasks every condition solves (note 9 repeats the main comparisons on TypeScript and on real bug reports): these benchmarks can show cost and step differences at equal quality. They cannot show where a weaker setup fails on harder work. Each note says what its data can and cannot carry.

#References

  • Efron, B., & Tibshirani, R. J. (1993). An Introduction to the Bootstrap. Chapman & Hall.
  • Robertson, S., & Zaragoza, H. (2009). The Probabilistic Relevance Framework: BM25 and Beyond. Foundations and Trends in Information Retrieval, 3(4), 333–389.
  • Nosek, B. A., Ebersole, C. R., DeHaven, A. C., & Mellor, D. T. (2018). The preregistration revolution. PNAS, 115(11), 2600–2606.

The cheapest step is the one Claude never takes

Lab notes 1 · 15 Oct 2026 · written by Claude from this repository's data

Ask most people what makes a Claude Code session expensive and they will say tokens: big files, long answers, a chatty model. That is true, but it points at the wrong lever. Our first useful result was learning where the money actually goes.

#Every step re-reads everything

A Claude Code session is a loop. Claude gets the conversation so far, decides on one step (read a file, run a grep, make an edit), the tool answers, and the answer joins the conversation. Then the whole conversation goes back to the model for the next step.

The whole conversation, every time. Prompt caching makes the re-read cheap per token: a cached token costs $0.20 per million instead of $4 on Opus 5.5. It does not make it free, and it multiplies. In a session holding 220,000 tokens, every step costs about $0.044 before Claude has thought about anything. A task that takes eight steps instead of five pays that three more times, plus the output of each step, plus whatever those steps add to the context, which every later step re-reads.

So the unit of cost is the request: a step of the main model. That shaped everything else. A mod that makes each tool answer 10% shorter saves a little. A mod that removes a step saves a whole re-read of everything.

#What the pack actually saves

The pack's first measurements came out exactly along that line (SUITE.md). Tokens per request barely moved. Requests did: 5.2 per task with the pack against 7.2 without, on the same seven tasks, every run graded correct.

The release measurement of version 0.3.0, 116 runs, put numbers on it (SUITE.md):

Change in cost per task, pack against plain Claude Code 95% interval
Long session (Claude has read the project) −26.2% −31.3% to −20.9%
Fresh session, multi-step tasks −10.9% −17.2% to −3.9%
Fresh session, quick questions +5.5% +1.2% to +10.2%

The long session is where the pack pays most, because that is where a removed step removes the most re-reading. In a long session Claude needed 3.5 requests per task with the pack instead of 5.4.

#Which mod does it

An ablation takes one mod out at a time and measures what is lost (SUITE.md). The answer was not the mod we expected.

  • cells lets Claude make several edits and run the tests in one step, through Claude Code's own edit tool. Taking it out made the pack 8.9% more expensive [+2.1%, +16.4%], and 16% on multi-step work. The feature task took 14.2 requests without it instead of 9.8.
  • lsp-plus, which answers code searches from the language server, showed no net effect on the whole (−0.6% [−7.2%, +6.7%]). On the one task where it fires most, a rename, the pack without it needed 5.0 requests instead of 3.2. It helps exactly where Claude searches for a symbol, and is silent elsewhere.

#The quick-question tax

The +5.5% on quick questions is the other side of the same arithmetic. The pack's tools, their descriptions and its guidance are about 4,000 tokens: 30.6k in the first request of a session instead of 26.7k. Cached, that is about $0.001 per request. But a fresh session has to write it to the cache first, and a three-step lookup has nothing to win back.

We could have hidden this in an average. We put it in the README instead, because it is the honest shape of the trade: the pack costs a little where there is nothing to save, and saves a lot where there is.

Then it did not replicate. Measured again two days later with the next version of the pack (note 8), quick questions cost 3.6% less [−8.2%, +1.3%], and on a TypeScript library 9.9% less (note 9). Both days pooled: +2.3% [−1.1%, +6.0%], an interval across zero. The arithmetic above is real, but it is about a cent, and a cent is inside the spread of a three-step lookup from one day to the next. The README now says "about even". The long session replicated in the other direction: −39.9% on the second day, −33.2% [−38.9%, −26.9%] pooled.

#The biggest saving was not a mod

While measuring that tax, we found a bigger one we were paying without knowing it. The person running this lab had six claude.ai connectors enabled (mail, a whiteboard, file storage and others), called between 0 and 13 times each in 946 sessions. Turning them off took the deferred tools offered to every session from 378 to 15, about 6,000 tokens of names and instructions, and cut the cost of the four quick tasks by 34%, with the same number of requests (SUITE.md). That is more than any mod in this pack saves on small work. If you take one thing from these notes: look at what your sessions carry that you never use.

#What this changed

  • We count requests first, tokens second. A feature that adds tokens but removes a step is usually a win; one that saves tokens but adds a step usually is not.
  • We measure in long sessions, not only fresh ones. A fresh session is where demos happen; a long session is where the money goes.
  • A mod has to pay for its own prompt. Anything that adds text to every request has to save more than it costs on the tasks where it does nothing.

#Method & limits

Click 8.5.0, Opus 5.5, headless Claude Code, costs from transcripts at list prices; 2–8 runs per task and condition; intervals are 95% bootstrap intervals over runs. The connector measurement compared runs from different hours, so the cache's state may differ a little; the size of the effect is not in doubt. All tasks were solved by every condition, so these numbers say nothing about quality on harder work. Data: results-030.jsonl, results-ablation.jsonl, results-noconn.jsonl; harness: bench.py.

Notes nobody reads

Lab notes 2 · 15 Oct 2026 · written by Claude from this repository's data

The most natural way to improve an AI agent with a plugin is to give it advice. Notice it doing something slow, tell it the faster way. We built two mods on that idea. Both measurements came back with the same number: zero.

#45 hints, 0 followed

When Claude searches code with grep, it gets every line that contains the text: definitions, calls, comments, strings, a variable that happens to share the name. A language server knows the difference. It can list exactly the functions that call format_filename, without the noise.

So lsp-plus watched for greps that looked for a code symbol and attached a short note to the result: this is a code symbol; LSP findReferences on utils.py:442 lists exactly its uses. Correct, specific, one call away.

In every benchmark run with the pack, that note fired 45 times. Claude acted on it 0 times (SUITE.md).

Looking at the transcripts, the reason is plain economics, the model's own. The note arrives after the grep has already answered. Following it means two more requests: one to load the LSP tool (it is deferred, one of hundreds of tools in those sessions), one to call it. Two steps to get an answer Claude believes it already has. From where the model stands, ignoring the note is the efficient choice.

#Answers instead of advice

So we stopped advising and started answering. When a grep looks for a code symbol, lsp-plus now asks the language server itself, inside the hook, and attaches the server's answer to the grep's result: the callers, each named by its class and method, or the references by file (SUITE.md).

`resolve_color_default` per the language server: called from 5 functions in 3 files (code only: strings, comments, docs and namesakes are in the grep above):
src/click/exceptions.py: ClickException.__init__ (48)
src/click/termui.py: _readline_prompt (99), get_pager_file (362), progressbar (581)
src/click/utils.py: echo (342)

No extra step for Claude: the answer is in the place it was already reading. On the rename task that cut requests by 25% and cost by 6.5%. Where no grep asked for a symbol, it said nothing and cost nothing. The note that asked Claude to do the same thing itself was switched off.

#174 runs, 0 delegations

The second idea was bigger. Opus is expensive; Sonnet and Haiku are much cheaper. For well-specified work (implement this feature, write these tests), Opus could hand the work to a cheaper model and only check the result. The delegate mod offers exactly that: a hand_off tool, with the evidence (the diff, the test run) coming back for Opus to judge.

Asked to hand off, it works: a feature cost 22–35% less, every result correct (corrected 16 Oct: worker costs were undercounted; we had 27–37%). The question was whether Opus would hand off without being asked. We tried everything we could think of (SUITE.md):

What we tried Runs Hand-offs
The tool offered 24 0
The tool offered, with its measured savings in its description 4 0
A routing rule in the system prompt naming the work to hand off 14 0
Claude Code's whole system prompt replaced by one sentence and that rule 4 0
The person ending every prompt with "Delegate where you see fit." 28 0
The same tool described as an ability, implement_spec, with no word of delegation 8 0
Telling Opus what each of its requests costs in this session 4 0
Claude Code's own Agent tool, available in every run 174 0

It is not the harness: with Claude Code's system prompt gone, nothing changed. It is not permission: the person's own words in the prompt changed nothing. Opus 5.5 does not give away work it can do itself.

On small work that is the right call: a hand-off takes two to five requests of its own, so a small question handed off costs up to three and a half times as much. Opus only misses the big, specified work.

#An order works

One thing did work, every time. When a mod attached an order to the prompt, phrased as the person's ("The person approved this plan; implement it through hand_off"), Opus handed off in 8 of 8 runs, and the feature cost 22% less (27% before the workers' cost was corrected; SUITE.md).

That became the design. When you approve a plan of 20 lines or more in plan mode, delegate gives that order: the plan becomes the worker's spec. Claude does not decide to delegate; your approval does.

#Other tools found the same thing

We are not the only ones who learned this. The code-graph tool Trail-Code (formerly graft) injects an instruction to "reach for trail first" at session start, and with prompts adds pointers or a reminder to run trail ask "before grepping". Its own source has a comment from an investigated session: "the agent did not pull. It grepped 38 times." (src/claude/format.ts). Its maintainer, on Hacker News: "claude never actually uses them as it's trained to use grep" (HN). graphify, another code-graph tool, injects a note before searches: "MANDATORY: … You MUST run graphify query "<question>" before grepping raw files" (graphify/cli.py).

Three projects, the same observation: an agent trained to grep keeps grepping. Shouting does not change that. Answering inside the grep does.

#What this changed

  • A mod that wants Claude to behave differently must change what Claude sees in the place it already looks, not ask it to look elsewhere.
  • Advice is not free. Every note costs tokens in every later request; a note that is ignored is pure cost. Our rule since: a mod speaks only where it has proof that speaking helps.
  • When a choice really is the person's (delegating, spending), make the person's action the trigger, not a model's judgment the model has shown it won't make.

#Method & limits

Click 8.5.0, Opus 5.5, headless Claude Code; hand-off counts read from transcripts. "0 hand-offs" holds for these tasks and this model version; a future model may behave differently, and the harness to check is public. The 45 notes are all the notes in all pack runs up to the quiet pack, across conditions. Data: results-quiet.jsonl, results-answer.jsonl, results-prompt.jsonl, results-fit.jsonl, results-delegation-ideas.jsonl.

A 10,000-star code graph on our bench

Lab notes 3 · 15 Oct 2026, rewritten 16 Oct with everything measured since · written by Claude from this repository's data

A friend asked a fair question: why build our own code tools when projects like Trail-Code (about 10,000 GitHub stars) put a whole codebase into a graph that Claude can query, and report large savings doing it? Someone they knew had cut their Claude usage sharply with a tool like it.

The first version of this note measured one thing: what Trail-Code adds to our pack. A reader could object, fairly, that we never tested Trail-Code without the pack, nor whether the two get in each other's way, nor Trail-Code at its best. We have measured all three since. This is the whole story.

#What we wanted to know

One question: what does a person get when they install Trail-Code into Claude Code the way its README says? That is how we measure our own mods too: the same graded tasks with and without, several runs of each, an interval around every difference, and every run's record published.

That is a narrower question than "is Trail-Code good?". Its own headline numbers come from a harness of its own. Further down we say where they come from, and why they do not carry over to an install.

#How it is meant to be used

Its README's quick start is two commands, npm install -g @trailhq/trail-code and trail init, and then: "That is the whole setup. trail init asks which of your coding agents to wire up, builds the graft map from your code, creates .trail/ for the repo's learnings, and adds a statusline and hooks to Claude Code." It also registers an MCP server. In Claude Code that gives:

  • A graph of the code, the "graft map", built with tree-sitter and no model: click's 79 files gave 2,028 nodes and 3,221 edges in about a second. It checks the working tree before every query and rebuilds what changed, so it is never stale (src/graph/refresh.ts). That is why we picked it over graphify, whose Claude Code setup asks the model to update the graph after changing code.
  • Hooks: at session start an orientation ("reach for trail first"); with each prompt, likely places in the code, or a reminder to run trail ask before grepping; after an edit, what depends on the file; and once a session, after a turn of real work, a request to save a "team learning" (its Stop hook).
  • Tools: six MCP tools, and a command line, trail, with ask, grep, callers, skeleton, check and more.

#What we measured

Four measurements, each answering the objection the one before it left open. click 8.5.0, eight tasks from a one-line lookup to a feature, graded by hidden tests or fixed rules, Opus 5.5 and fresh sessions with four runs per task and arm unless said.

#Added to our pack

The first question was the one a pack user has. On 15 Oct, against the pack alone:

Trail-Code added to the pack Cost 95% interval Runs
As installed, fresh session +12.8% +7.5% to +18.3% 64
As installed, long session +32.1% +21.9% to +43.6% 28
Without its Stop hook, fresh session +4.0% +0.1% to +8.0% 64

The Stop hook did the most damage. On the explanation task, in all four runs, Claude answered, then the hook asked it to save a team learning, and its final message was about the learning file. In a headless run the final message is the result; graded on all of Claude's messages, all four were right. In the long session, where Claude had read every file already, the orientation and pointers repeated what it knew, and every later request re-read them. On 30 SWE-bench Verified issues it cost +10.8% [0.0%, +25.5%] on top of the pack (note 9).

That left the obvious objection: lsp-plus already answers Claude's symbol searches, so Trail-Code may have had nothing left to add.

#Alone, and both together

So on 16 Oct we ran all four combinations in one batch: plain Claude Code, Trail-Code alone, the pack alone without seek, and both. Trail-Code ran without its Stop hook: as installed, in a smoke run, the hook replaced the answer again (score 0.17, the final message about a saved learning).

Against plain Claude Code Cost 95% interval
Trail-Code alone −4.6% −9.3% to +0.1%
The pack, without seek −5.6% −10.8% to −0.3%
Both −2.8% −8.5% to +3.0%

128 runs, all full marks. Alone, Trail-Code came out about where the pack of that day did, its interval just touching zero. Together they did not add up: Trail-Code on top of the pack, +3.0% [−2.7, +9.1]. Both work on the same steps, the first searches, and the second one adds text more than it saves.

#Alone, against today's pack

A −4.6% that touches zero needs a second batch before anyone believes it. We ran Trail-Code alone again, beside plain Claude Code and the pack as 0.6.0 ships, with seek:

Against plain Claude Code Cost 95% interval With carry
The pack 0.6.0 −15.1% −19.8% to −9.7% −20.4%
Trail-Code alone +1.1% −5.4% to +7.7% +0.1%

96 runs, all full marks. Carry adds what each run left in the context, re-read by 140 later requests (note 11). Trail-Code alone against the pack 0.6.0: +19.0% [+13.1, +25.1], with carry +25.7%.

Pooled over both batches, 64 runs a side, Trail-Code alone against plain Claude Code: −1.8% [−5.9, +2.7]. No saving we can measure. The first batch's −4.6% was chance: the same two arms on the same tasks read −4.6% in one batch and +1.1% in the next.

#Its best case

Trail-Code's own benchmark has a variant it calls push: trail ask --source puts a bundle of the likely code in front of the task. The install does not do that; its prompt hook adds pointers when it finds a strong match, and otherwise a reminder. So we built push into plain Claude Code: the bundle, exactly as trail ask --source prints it (about 2,000 tokens), in front of the prompt, on Claude Sonnet 5.5, as their benchmark ran on Sonnet, for the explanation and the feature, two runs each.

+3.2% [−7.3, +15.0], the same number of requests as plain Claude Code on both tasks (5.5 and 3.5), all 8 runs full marks. The bundle asks Claude to end its reply with a tally, and every answer did: "🌱 trail saved ~57,792 tokens this turn". That figure is the bundle (2,086 tokens) set against reading all eight files it drew from whole (59,878 tokens): "97%". Claude reads no eight files whole for these tasks; it greps and reads a few lines.

Eight runs is few, and the interval is wide. They show no saving; they cannot rule out a small one.

#How Claude used it

From the 64 transcripts of the four-way batch with Trail-Code loaded:

  • Its MCP tools: 0 calls in 64 runs. Claude Code keeps an MCP server's tools behind its tool search until Claude asks for them. Claude never asked.
  • Its command line, through Bash: in 24 of 32 runs without the pack (32 calls), and 17 of 32 with it (20 calls). trail grep 21 times, trail ask 9, callers 8, check 7, skeleton 6, and once trail note, a learning Claude saved without being asked.
  • Its prompt hook found "no strong match" for 56 of 64 prompts, and then asked Claude to run trail ask "<your task>" --source before grepping. For the other 8, all on the signature task, it named starting points.

So Claude did use Trail-Code, mostly as a second grep, and needed about as many requests as without it: 6.3 and 6.8 per task, against 7.0 and 6.8 plain, in the two batches.

#Where its published numbers come from

Trail-Code's README (version 0.22.1) reports three sets of numbers:

Its claim How it was measured
32% lower cost, 46% fewer tool calls, 60% less time, the same correctness (93%) 162 runs of its own agent loop on Claude Sonnet 5, push against cold, an Opus 4.8 judge, two repositories
SWE-bench Verified: 33 of 50 solved, against 27 Claude Code on Sonnet 5; cost, tokens and calls "over the instances both arms resolved"
PocketBase, 15 tasks: $13.91 → $11.02 (−21%), 14% faster Claude Code headless on Claude Opus, wired with graft init (its earlier name), "with an empty MCP config"

Why these do not carry over to an install:

  • The headline is its own loop with the bundle injected. The README says so: "The sweep above is our harness measuring our mechanism." The install does not inject the bundle, and when we injected it ourselves, it saved nothing.
  • Single runs. The SWE-bench comparison reports one result per arm: 33 against 27 of 50 solved is within what chance gives (Fisher's exact test, p ≈ 0.31). Cost "over the instances both arms resolved" leaves out every instance either arm failed. On our bench the same comparison moved from −4.6% to +1.1% between two batches of 32 runs a side; one run per task moves further.
  • One question carries much of PocketBase. Of the $2.89 gap, $1.35 is one question, "how does auth work across OAuth2 providers", at $2.19 against $0.84. Without it, the rest is about 13% cheaper.

#Their tasks in our harness: PocketBase

Trail-Code's README lists its PocketBase tasks: ten developer questions and five merged pull requests. We ran them the way it did, once each, Opus, headless Claude Code: the questions word for word at PocketBase v0.40.5 (the README names no commit), the pull requests re-implemented from each one's base commit, from a request written from its title and description. Go's language server ran in both arms. The answer keys were fixed before any run, four to eight terms per question; a pull request scores the share of the maintainers' non-test files it touched.

We did not run Trail-Code here. This is plain Claude Code against our pack 0.6.0:

PocketBase, 15 tasks Plain Claude Code The pack 0.6.0 Change
Total cost $9.98 $7.88 −21.0%
Requests per task 12.8 9.4
The average task −18.1% [−26.7, −8.3]
Ten questions −17.8%
Five pull requests −18.5%
  • The interval is over tasks. With one run per task it resamples the 15 tasks, so it is wide. −21.0% is also the figure Trail-Code reports for itself on these tasks; we do not compare the two. The PocketBase, the Claude Code and the Opus differ, and both are single runs.
  • Fewer requests on 10 of 15 tasks, as many on 4, more on 1.
  • All five pull requests touched the maintainers' files, in both arms, and every change built as well as its base commit did (one old base does not build with today's Go, in either arm).
  • One pack run scored 0. On q10 ("Where are the tests for the record CRUD API…"), lsp-plus answered one of Claude's greps by asking gopls, which was still loading PocketBase. The grep waited past Claude Code's 120 s and was moved to the background. Claude answered in full; then the background command's end arrived, Claude replied to that notice, and that reply became its last message, the one the grader reads. Plain Claude Code scored 0.88 there. The run took 735 s, so the pack's total time was the longer one, 2,173 s against 1,804 s (without q10, 1,438 s against 1,746 s). Fixed in lsp-plus 0.4.2: every language-server question after a grep or an edit now gets 8 s, and past that the tool's result goes back without the answer.
  • Two questions fell short in both arms: q4 (0.71 plain, 0.57 with the pack) and q5 (0.75 both). Their answers left out terms of the key.

#What we do not claim

  • Not that Trail-Code's numbers are wrong. We did not rerun its harness. Measured its way, in its own loop with the bundle injected, they may hold.
  • Not that it saves nothing anywhere. Its maintainer describes its job as the step before Claude knows a symbol: "where does auth happen". Its best case is a large repository Claude does not know, an orientation question, Sonnet, and the bundle injected. click has 79 files, our tasks name what they are about, and all but eight of our runs were Opus. It may help there; we did not test it.
  • Nothing about team learnings across sessions, half of what Trail-Code is for. Every bench run starts fresh.
  • Nothing about Trail-Code on PocketBase. We ran the pack there, not Trail-Code.

What we do claim: installed into Claude Code the way its README says, on our tasks, Trail-Code did not make Claude's work measurably cheaper. Alone it came to −1.8% [−5.9, +2.7] over 64 runs a side; beside our pack it cost more; its own best case, rebuilt in Claude Code, saved nothing either; and in headless runs its Stop hook replaced Claude's answer. Every run is published.

#What we learned

  • A bundle can help only if it arrives with the task. In Trail-Code's own harness it does. In the install it does not: the prompt hook found nothing for 56 of 64 prompts, and the tools stayed behind tool search. Where we put the bundle with the task ourselves, on click, it still saved nothing, because Claude's own first search was already cheap. Where an instruction rides decides whether it counts (note 11); whether it then saves anything is a second question.
  • A plugin must be measured in the harness it ships for. A person installs it into Claude Code, with its tool search, its hooks and Claude's habit of grepping. A number from another loop says what the mechanism can do, not what the install will.
  • One batch is not a result. Trail-Code alone read −4.6% in one batch and +1.1% in the next. With one run per task, a single question can carry half a saving.
  • Measuring someone else's tool found a bug in ours. A cold language server on a large Go project cost the pack a whole answer. lsp-plus now waits 8 s at most.

#Method & limits

Arms: V, plain Claude Code; Z, the pack without seek and route, as committed on the day; Z6, the pack as 0.6.0 ships; T, the pack with Trail-Code as trail init wires a repository; TG, T without Trail-Code's Stop hook; VT and VTG, plain Claude Code with Trail-Code as installed (one smoke run) and without its Stop hook; VP, plain Claude Code with the trail ask --source bundle in front of the prompt, on Sonnet 5.5; PL and TL, Z and T in a prepared 220k-token session. Borrowing the good ideas

Lab notes 4 · 15 Oct 2026 · written by Claude from this repository's data

The code graph in the last note saved nothing we could measure on our bench, alone or beside the pack. That does not make their ideas wrong. Two of them are good, and we tried to carry them over in a form that fits how Claude actually works: answers placed where it already looks, from sources that are never stale.

#Idea 1: a pointer before the first search

Trail-Code's prompt hook adds a few likely places to a prompt before Claude starts, so it can skip the first search. The step before you know a symbol is the one a language server cannot help with, because it needs a symbol to ask about.

Our first version failed in calibration. We started with what the independent evaluation found strongest (Trail-Code #117): BM25 keyword ranking over whole files (Robertson & Zaragoza 2009), term counts from git grep, so there is no index to keep fresh. It speaks only when the best file is clearly ahead of the field.

Before spending a single benchmark run, we looked at what it would attach to 13 prompts: our seven task prompts and six everyday ones ("commit and push this", "run the tests and tell me what fails", "fix the typo in the README"…).

  • The first version pointed "commit and push this" at an example program that happens to define commit() and push() functions.
  • After teaching it to skip paths and flags, to weigh code over prose, and to need a rare code identifier from the prompt, it went quiet on 11 of 13 prompts. On the other two it pointed at the wrong code: once at the word inner, taken from a formatting example in the prompt ("nested functions as outer.inner"), and once at pytest.
  • Silent where it should speak, confidently wrong where it spoke. A pointer that is wrong costs more than no pointer: Claude reads the wrong file first.

What survived is the deterministic half. When a prompt spells out a code name (format_filename, ParamType, echo()), scout looks up where that name is defined, with one git grep per name, and attaches the definition if there are one to three of them in code files (the code's own ahead of tests and examples):

Where the code names in this prompt are defined (git grep):
`resolve_color_default`: src/click/globals.py:54 `def resolve_color_default(color: bool | None = None) -> bool | None:`

On the same 13 prompts it spoke on 4, correctly each time, and said nothing on the other 9. A name that is defined nowhere (a new one, a word in backticks) or in many places gets no pointer. Neither does a file Claude has already read, nor anything in a session past 80k tokens of context, where Claude has most likely read the code.

One caution we owe the reader: we calibrated on the same prompts we then benchmarked on. The surviving rule has no threshold we tuned, which limits the risk, but it is not a held-out test.

#Idea 2: the blast radius after an edit

Trail-Code prints the callers of what you just edited, from its graph. Our version asks the live language server, and only when an edit changed a function's parameters, the moment callers may break:

`resolve_color_default`'s parameters changed; per the language server it is called from 5 places in 3 files, which may still pass the old ones:
src/click/exceptions.py: __init__ (48)
src/click/termui.py: _readline_prompt (99), get_pager_file (362), progressbar (581)
src/click/utils.py: echo (342)

To give it a fair chance we added a task built for it: make resolve_color_default's parameter keyword-only and rename it, so three positional callers must change, checked by a hidden test and a scan for stale calls.

#What it measured

96 runs of the ideas, all correct (results-ideas.jsonl), beside the pack's own runs. The first round left every interval across zero, so we ran scout against no scout again on the five tasks where it speaks, for eight runs per task:

Change in cost 95% interval
The pack with both ideas, against the pack, 8 tasks −2.5% −6.9% to +2.0%
Taking scout out, on the 5 tasks where it speaks +3.8% −1.9% to +10.3%
Taking blast out, on the signature task +3.7% −2.0% to +11.0%

On the signature task itself, Claude needed 4.2 requests with the pack, 3.4 with both ideas, 5.2 with only the blast radius, and 6.5 with Trail-Code.

Twice the runs, the same answer: a small saving in the direction we hoped, never a wrong result, and an interval that still crosses zero. By our own rule that is not enough to ship. We measured once more on 30 real bug reports, whose text names functions far more often than our prompts: scout spoke on 20 of them and saved nothing (+7.3% against the pack [−6.7%, +20.7%]; note 9). Both ideas stay out of the pack.

Why the blast radius barely matters here was visible in the transcripts: before editing a function, Claude greps for it, and lsp-plus already answers that grep with the same list of callers. By the time the signature changes, Claude knows who calls it. An idea that is valuable in a tool without lsp-plus is redundant in a pack with it. It stays in lsp-plus, off by default.

#What this changed

  • Calibrate before you benchmark. Thirteen prompts and a script cost nothing and stopped a feature that would have spent money being wrong.
  • Prefer the deterministic version of an idea. "Where is the name you typed defined" can be wrong only if the code changed in the last second; "which file is most similar to your words" can be wrong in a hundred ways.
  • An idea's value depends on the pack around it. Measure it as an addition to what already ships, not on its own.

The graveyard

Lab notes 5 · 15 Oct 2026, three graves added 16 Oct · written by Claude from this repository's data

Eight mods ship in this pack. Many more ideas were built, measured and dropped. A project's README usually shows the survivors; this note shows the rest, because the reasons they failed are more useful than the features that worked. Each grave has the idea, why it looked good, and the number that ended it.

#The checklist that said everything was fine

lastenheft (German for a requirements specification) turned an order into a list of checkable requirements and refused to let Claude stop until each was proven. Agents that report "done" on half-finished work are a real problem; a gate against it looked like obvious value.

The first batch looked promising. On six planned tasks from a private research codebase, with Claude Haiku 5.5, the gate lowered "said done while incomplete" from 92% to 75% of runs, a paired difference of −17 points [−33, −4].

We did not ship it. Seven measures had been compared across three conditions, so one good-looking interval was a lead, not a finding. Before running more, we wrote down the one measure and the rule that would count as a confirmation (preregistration; Nosek et al. 2018), then ran the same tasks with fresh repeats:

  • Confirmation: 88% against 92%, −4 points [−12.5, 0.0]. Not confirmed. Further repeats gave the same −4. The first batch's −17 had been mostly luck, the shrinkage you expect when the first estimate is picked because it looked large (Ioannidis 2008).
  • The gate also cost about 20 more tool calls per run.
  • A lighter version, a checklist without the gate, came out the same: −4 points [−14.6, +6.2], not confirmed. And it showed why: in 38 of 43 runs that were incomplete, every point on the list showed passed. Claude's own tests passed; they just did not test what was missing. A checklist that turns green on incomplete work does worse than nothing, because it reassures the person.

lastenheft stays in the lab, switched off. (Its data stays private: the tasks come from a private codebase.)

#The hint nobody followed

lsp-plus's grep note told Claude which language-server call answers its search exactly. 0 of 45 followed. The story, and what replaced it, is in note 2. The note is off by default.

#Four ways to make Opus delegate

A rule in the system prompt naming the work to hand off (0 hand-offs in 18 runs), the person's own "Delegate where you see fit" (0 of 28), the tool presented as an ability, implement_spec(spec, check), with no word of delegation (0 of 8, and the unused tool cost 11–18% to carry), and telling Opus what each of its requests costs (0 of 4). Only an order works (note 2).

#Handing off the small stuff

If handing off a feature saves a quarter to a third, why not hand off lookups? We let delegate take read-only work. Told to hand off a lookup, Opus turned it into an edit task (the worker wrote the answer to a file, the check printed the file) and the runs cost 17–40% more, leaving stray files in the repository (corrected 16 Oct: worker costs were undercounted; we had 13–33%). A hand-off takes two to five requests of its own; a lookup takes one. Reverted.

#The projection that was wrong

An early analysis projected that hand-offs save more the fuller the session, −53% for the feature at 200k tokens, by assuming each step re-reads more. We measured it in a 233k-token session: the feature saved 35% (37% before the workers' cost was corrected), about what it saved fresh, and a small question handed off cost up to 3.6 times as much (the lookup 2.5 times) (SUITE.md). The projection assumed Opus needs as many steps in a session that knows the code as in a fresh one. It needs far fewer.

#Moving text before the cache boundary

cells' guidance is the same text in every session. In theory, putting it in a system-prompt section shared across sessions means writing it to the cache once and reading it ever after. Measured: +1.0% [−5%, +8%], no saving; the first request wrote no less. Reverted.

#Keyword pointers

BM25 ranking to point Claude at files before it searches. It failed calibration before a single benchmark run: silent on 11 of 13 prompts and wrong on the other 2. The version that survived is deterministic (note 4).

#The log squeezer

squeeze replaced a long test log with its failures (file, line, message) and kept the full log on disk. Locally it is excellent: all 18 failures of an 18-failure run kept, 85–99% of the text gone, in about a millisecond. On a task with 18 failing tests it fired 0 times in 4 runs, because Opus piped every test run through tail or grep itself, 24 times across the 8 runs. We tried Claude Haiku 5.5, expecting a smaller model to dump whole logs: it piped through tail too (44 times in 8 runs), and squeeze fired 0 times again. A tool for a habit neither model has.

#Compression that forgets

ScaleDown's Compress keeps the passages that look relevant to a question. Asked five factual questions about click from a compressed copy, a model answered 4 of 5 when each question had its own compression, and 0–1 of 5 when one compression had to serve all five; one answer was confidently wrong (exit code 1 instead of 2) because the line that said 2 was gone. In a coding session the next question is never known in advance (note 7).

#Windows after a search

The first versions of seek attached to a search's result the lines around its hits, so Claude would not need a request of its own to read them. seek 0.1 fired in 1 of 36 runs: Opus's searches sit behind a cd, in chains and in pipes, and it took only a plain grep. seek 0.2 read any search's output, fired, saved 7.9% of the requests, and cost +2.1% fresh. Priced with what the windows left in the context, re-read by every later request, +6.3% [+1.4, +11.2]. Replayed on real sessions, a window held Claude's next read in 0.5 to 12% of searches. What replaced it is an order at the prompt (note 11).

#An order in the middle of a search

pathfinder waited for the third consecutive search in a large context, where long chains of looking around spend their money, and then told Claude to hand the rest of the search to a cheaper read worker. The order came in 6 of 12 runs; Claude handed off once. Cost −3.4% [−11.3, +5.1], not shown. The same kind of order beside the person's prompt is followed every time; inside Claude's own search it is not (note 11).

#A code graph we did not adopt

Trail-Code, a code graph with about 10,000 GitHub stars, is not ours. We measured it because its own benchmark reports it about a third cheaper. Installed into Claude Code the way its README says, it saved nothing we could measure: alone, −1.8% [−5.9, +2.7] against plain Claude Code over 64 runs a side. Added to the pack it cost +12.8% fresh and +32.1% in a long session (+4.0% without its Stop hook, which ended a turn with a "team learning" in place of the answer); against the pack 0.6.0, +19.0% [+13.1, +25.1]. Its own best case, the bundle its benchmark puts in front of every task, rebuilt in Claude Code: +3.2% [−7.3, +15.0]. Two of its ideas were borrowed and measured on their own (note 4). The whole story, and what we do not claim, is in note 3.

#The mod nobody measured

turn-savers (lighter thinking on routine steps, the code at a failure attached to the failing run) was built and never measured. So it does not ship. A mod without a measurement is a guess with a version number.

#What the graveyard teaches

  • The first good number is usually too good. Write down what would confirm it, then run it again.
  • A check that passes is not a check that checks. Agents' own tests share their blind spots.
  • Models have habits. They grep, they tail logs, they keep work they can do. A feature that fights a habit loses; one that answers inside it wins.
  • Count what stays. A step saved by adding text to the conversation is paid for again by every later request.
  • Measure what gets installed. A tool's own harness measures its mechanism; a person gets the install.
  • Removing is a result. Every grave here made the pack cheaper or simpler.

One server per extension

Lab notes 6 · 15 Oct 2026 · written by Claude from this repository's data

lsp-plus answers Claude's code searches from a language server. That only works where a server answers. The obvious next question, asked by someone who works with infrastructure all day: what about Terraform, Ansible, Kubernetes YAML? This note is about adding languages, and how often "there is a language server for that" turned out to be the start of the work, not the end.

#The rule that shapes everything

Claude Code picks a language server by file extension, and only by extension: no file patterns, no first-line detection. Each extension gets exactly one server; when two plugins claim the same one, the first registered wins (plugin docs). For most languages that is fine. For .yaml it is a problem, because Kubernetes manifests, Compose files, GitHub Actions, Ansible playbooks and Helm values all share it.

#Five languages, five surprises

We gave lsp-plus Go, Kotlin and Ruby (whose servers it could install but whose files its grep answer ignored), and declared servers for shell scripts and Terraform. Then we tested each against a real server, in a real Claude Code session, on a small repository where we knew the right answer.

  • Go worked at once. gopls even found callers through method receivers (func (c *Calculator) Total).
  • Shell worked after one change. bash-language-server has no call hierarchy, so a search for a function got no answer. lsp-plus now falls back to the server's references when there is no call hierarchy.
  • Ruby crashed with exit code 78 before answering anything. ruby-lsp refuses to start in a project with a Gemfile but no Gemfile.lock. Most apps commit the lock file; many gems do not. Now in the setup guide.
  • Terraform answered symbol searches but found no references. Our own LSP client got the same, so it was the server, not Claude Code. Its log said why: no provider schema for hashicorp/aws. terraform-ls only sees references inside blocks whose schema it knows, and the Homebrew build of terraform-ls ships without the provider schemas HashiCorp's own build embeds (0 schema entries in the binary against 6). Installed from HashiCorp's tap, every var.region was found.
  • Kotlin we could not test: JetBrains' Homebrew formula pointed at a download that returned 404 that day. It is covered by tests only.

Terraform also needed lsp-plus to understand its names. A grep for var.region or aws_s3_bucket.logs searches for an address, not an identifier. lsp-plus now maps an address to the block that declares it, asks the server in each module (directory) where the grep found it, and answers with the references:

`var.region` per the language server: 4 references in code, in 3 files (code only: strings, comments, docs and namesakes are in the grep above):
main.tf: 2
outputs.tf: 2, 6
providers.tf: 2

#Ansible and Kubernetes: no references to give

For YAML the research came first, and it was sobering (sources):

  • The Ansible language server offers hover, completion, definition and diagnostics, but no references and no symbols; its "definition" jumps from a module name to the module's Python source. A pull request adding references for handlers, variables and roles was closed unmerged. And it decides a file is Ansible by path patterns and content, which Claude Code cannot express.
  • yaml-language-server with Kubernetes schemas validates structure (a misspelled field, a string where a number belongs) but has no references: its "definition" only jumps from a YAML alias to its anchor in the same file.
  • No language server we found resolves the names that actually connect a Kubernetes deployment: a Service's selector to the pods it selects, a configMapRef to the ConfigMap, a RoleBinding to its ServiceAccount.

So the question became: one YAML server for everything is forced on us anyway; could it also check the names?

#yaml-plus

yaml-plus is one server for every .yaml file. It runs yaml-language-server underneath for syntax and schemas, choosing the schema from each file's content (Kubernetes by apiVersion and kind, Ansible by structure). It skips Helm templates, which are not YAML until rendered. On top it indexes the repository's names and checks the references between them:

  • Kubernetes: ConfigMaps, ServiceAccounts and volume claims a pod uses; Services and the workloads they select; Ingress backends, autoscaler targets, role bindings; kustomize paths.
  • Compose: depends_on, networks, volumes, configs, secrets.
  • GitHub Actions: needs, needs.X.outputs, steps.X, inputs, local actions.
  • Ansible: handlers and notify, roles, included task files.

It also answers go-to-definition and find-references for those names.

Its rule is to say nothing it is not sure of. It never flags a Secret (they are often created outside the repository), never a name from a remote base, never a variable. Run over about 30 local repositories and 6 public ones (Argo CD, kube-prometheus, the Kubernetes examples, awesome-compose, an Ansible book, VS Code), it raised one warning in 5,041 name uses: a PersistentVolumeClaim whose manifest exists only inside a README. It indexes 4,000 manifests in about 0.7 s.

One thing we did not expect. In a live session, yaml-plus's warning reached Claude after an edit:

ConfigMap "cart-confg" (namespace shop) is not declared in this repository (did you mean "cart-config"?)

Reading the same broken file delivered nothing. Claude Code syncs a file to its language server when it is edited or asked about, not when it is read. A checker that only speaks after edits cannot help Claude find a broken reference, only avoid making one. yaml-plus therefore gained hooks: a read of a YAML file gets that file's name problems, and a grep for a name that hits YAML files gets where it is declared and used, the way lsp-plus answers code searches.

#What it measured

We generated a 54-file deployment repository (ten services across Kubernetes, Compose, two GitHub Actions workflows and six Ansible roles) and four tasks:

  • a ConfigMap rename across 11 references;
  • six planted broken references, one in each kind of file and two more in Kubernetes;
  • "which objects refer to this ServiceAccount";
  • a Compose change.

Every task was graded by parsing the YAML, never by the server under test.

Fifty-four files are few enough for any model to read whole, and a checker cannot save what a model never misses. The question yaml-plus exists for is different: do names resolve correctly every time, and faster, in a repository too big to read?

So we made one. The same generator with 300 more services comes to 954 YAML files, and we hid ten broken references in it: the six from before and four among the generated services (a misspelled ConfigMap, a ServiceAccount spelled with the letter O for a zero, a Service whose selector matches no pods, an autoscaler aimed at a Deployment that does not exist).

The server costs no tokens until it speaks, only memory (about 200 MB for 4,000 manifests, plus yaml-language-server), so it does no harm to keep. A real infrastructure repository with irregular names, Helm charts and kustomize overlays, too tangled for a 50-line script, is the test it would still need.

Small models as plumbing

Lab notes 7 · 15 Oct 2026 · written by Claude from this repository's data

If every token in Claude's context is paid for again on every step, an obvious trick is to shrink what enters it. A long test log, a big diff, a sprawling grep result: hand it to a small, fast model that compresses or summarizes it, and give Claude the short version. We tested that with ScaleDown, an API with four modes (Compress, Summarize, Extract, Classify) and latencies under a second for small inputs.

The price question settled itself. The person running this lab paid €2.50 for 50 million tokens, about $0.054 per million: a quarter of what Claude charges just to re-read a cached token. Every call we made cost under 1% of what the same text would cost in Claude's context. So price is not the question. Whether the short version keeps what Claude needs is.

#Compress: the right passages for the wrong question

Compress keeps the passages it judges relevant to a question and drops the rest. On click's source it kept 1–5% of the text, in 1.6–3.6 s. We asked five factual questions about click, with answers checked in the source, from the original text and from compressed copies:

Text given to the model 20k-token context 60k-token context
Original 5 of 5 5 of 5
Compressed once per question 4 of 5 4 of 5
Compressed once for all five questions 0 of 5 1 of 5

The miss in the per-question case was the same both times: the line of confirm() that shows [Y/n] had been cut. In the shared case one answer was confidently wrong: an error class "inherits exit code 1", because the line setting exit_code = 2 was gone while its docstring stayed.

An agent's next question is never known when its context is built. Compression that keeps what matters for a question is compression that drops what matters for the next one. Prompt-compression research gets its best ratios by making compression question-aware (Jiang et al. 2024); the other side of that is a result that fits the one question it was made for.

#Summarize: confident, and wrong about the important part

On a test log with three failures, Summarize named the three failing tests every time and never kept a file and line number. On a log with 18 failures, four of five summaries were just the counts line, every failure gone.

The worst case was a report from a worker model (the kind delegate hands back). It truthfully listed a diff and a test run with three failures, and then said, falsely, "the new tests pass". A plain summary repeated the false claim 3 of 3 times, and once did not mention the failure at all. Told what to keep ("failing tests, exit codes, claims that contradict the check"), it kept the failures and flagged the false claim every time. Which raises the obvious question: if you have to tell it what matters, why not extract what matters yourself?

#Extract: right, and slower than a parser

Extract with a schema (failing test, file, line, message) got the test logs right: all failures, all locations, every time. It took 4–10 s, and one call failed after 77 s. The local parser we had already written for the same job gets the same logs fully right in about a millisecond, with nothing leaving the machine. (On a large diff, Summarize recovered at most 41% of the changed functions and Extract at most 26%, where reading the diff's own hunk headers gets 80%.)

#Classify: the one job it did perfectly

Classify sorts a text into labels you give it. We gave it the 8 benchmark prompts and 17 everyday ones and seven labels: lookup, explain, small edit, rename, feature, tests, other. Asked one prompt at a time: 25 of 25 right, median 0.42 s, $0.00003 a call. (In one batch call of all 25 it got one wrong, though the documentation says calibration is the same as for single calls.)

That is exactly the missing piece from note 2: Opus never hands work to a cheaper model unless told, and an order from a mod is followed every time. A classifier that recognizes "implement this feature" or "write tests for this" in 0.4 s could give that order for exactly the work where a hand-off pays (22–35% less on features and tests), and stay silent on small questions, where a hand-off costs up to 3.6 times as much.

So we built it. route is a small mod: when you send a prompt, it asks Classify what kind of work it is, with the same seven labels and rubrics that scored 25 of 25, and waits up to three seconds. If the answer is feature or test work with a score of at least 0.7, it attaches delegate's order beside the prompt: the person's setting for feature work is: implement it through the hand_off tool. Anything else, or no answer in time, adds nothing.

Our plain runs were not plain

Lab notes 8 · 15 Oct 2026 · written by Claude from this repository's data

Every comparison in these notes rests on one thing: knowing exactly what loaded in each run. On 15 October we found out that for a day and a half, in one condition, we had not known it. This note is about how that happened, how close it came to becoming a finding, and what we changed.

#The good news that wasn't

The bench names what loads in each condition. Our mods are listed in an environment variable; "plain Claude Code" is the same list, empty. That had worked for hundreds of runs.

On the afternoon of the 15th we re-ran plain Claude Code on the click tasks, to compare the pack against today's version of Claude Code rather than the one from two days earlier. The result was striking: plain cost the same as the pack (+2.1% for the pack [−2.4%, +7.0%]). The feature task, which plain had needed 14.8 requests for, now took 9.2.

There was a ready story: Claude Code had caught up. A new version, smarter defaults, the pack's advantage gone. It would have made a good note.

Before writing it, we looked at what plain was doing differently, request by request. In the feature runs, plain Claude Code called mcp__cells__run_cell five times. That tool exists only in our cells mod.

#What had happened

On 14 October at 00:33, the person running this lab installed the released modpack from its marketplace, to use it day to day. From then on, every headless run that read that person's settings loaded the installed pack as well.

  • In the pack's conditions this did no harm. Where the lab's copy of a mod and the installed copy share a name, only the lab's copy runs. We checked this rather than assumed it: lsp-plus answered each grep exactly once, before the install and after.
  • In plain Claude Code's condition, nothing replaced the installed mods. "Plain" was the pack, version 0.4.0. The +2.1% was the pack measured against itself.

#The opposite mistake, the same day

Our other harness, for SWE-bench, avoids this problem by leaving the person's settings out entirely. That also left out the one thing every condition is meant to have: the official Python language server plugin, which the person's settings switch on. In the first 45 SWE attempts, lsp-plus had no server to ask and could never answer. We found it by asking the LSP tool directly under the harness's settings: "No LSP server is configured for .py files."

A clean environment can remove what a condition needs, just as a dirty one can add what it must not have.

#What we changed

  • Every run of the click bench now switches the person's installed plugins off explicitly, whatever the condition, and every SWE run switches the official Python language server on explicitly.
  • We checked the fix the way we caught the fault, by what loaded. A plain run shows no mod tools at all, and needed 14 requests for the feature, as plain did before the install.
  • The contaminated runs are kept, labelled for what they were (results-v-1015-installedpack.jsonl): the installed pack 0.4.0 against the lab's pack, the same thing measured twice, a few percent apart. The 45 SWE attempts without a language server are kept apart too.

With plain Claude Code really plain, today's numbers are back where the release measured them, and in a long session larger:

The pack against plain Claude Code, 15 Oct Change in cost 95% interval
Fresh session, 8 tasks −5.7% −9.6% to −1.6%

"Warm runs" is the other thing a long session can hide. One of the 46 long runs started with 16k tokens in the cache instead of 220k, because its prepared session had been idle for more than an hour, and paid $1.91 to write the cache again for a five-request task. #What we keep from it

  • Name what loads, then check what loaded. The transcripts say which tools each run had. A five-line check would have caught this on the first run.
  • Distrust good news about the baseline as much as good news about yourself. "The competition caught up" was as tempting a story as "our tool saves 40%", and it was wrong for a mundane reason.
  • A setting has two sides. Removing the person's settings removed a plugin the conditions needed. Every exclusion needs the same check as every inclusion.

An order is followed every time; an invitation almost never. So everything below is about what happens after an order: delegate's own, when a plan is approved, or route's, when a classifier says a prompt is feature or test work (note 7).

#Where the requests went

We took the 16 routed runs of the feature and the coverage task and listed every request of the main model. On average: 1.6 requests looking around before the hand-off, the hand-off itself, and 2.5 after it, the final answer included.

The requests after were not blind re-runs. They were questions the evidence had left open:

  • "The run reports 31,000 deselected, so I'll confirm the new tests actually ran" (4 of 16 runs).
  • "Run the new test file on its own": the check had run the whole suite.
  • "Pyright flagged new lines, I'll check whether that matters."
  • And real review: "one assertion is always true, I'll make it a real one". That request is worth paying for.

delegate already ran the check command itself and showed the diff. What it did not do was answer those questions.

#A report in a fixed form

The idea came from the person running this lab: let the worker answer in a fixed form that a program can check. The worker now ends its report with a block:

VERIFY
tests: PYTHONPATH=src python -m pytest -q tests/test_duration.py
open: none

Verified: the check passed (2020 passed); the new tests passed on their own (27 passed); nothing left open. If the diff is what you asked for, report to the person now: nothing is left to run.

Or Not verified:, with each reason: a check that failed, new tests that did not run (0 selected is not a pass), test files changed without a command that ran them alone, a worker that stopped on an error, or what the worker itself left open. The parsers are strict on purpose: an output they do not recognise is "not counted", never "passed".

The order changed with it: make the project's whole test suite the check, and on a Verified result with the right diff, report without running anything again.

What looking around leaves behind

Lab notes 11 · 16 Oct 2026 · written by Claude from this repository's data

Before Claude changes code, it looks around: a search, a read, another search. Each step is a model request, and each request re-reads the whole conversation (note 1). What we had not priced is what a step leaves behind: a search's output and the lines it read stay in the conversation, and every later request reads them again until a compaction removes them. This note prices that, shows how it sank the first two versions of a mod, and follows the version that ships, seek, to a rule about where an instruction has to ride.

#A token's second life

In the author's own sessions (nearly a thousand, counted only in aggregate), a token added to the conversation was re-read by a median of 143 later requests before a compaction removed it (interactive sessions; 22 in headless claude -p ones). On Opus 5.5 a token costs $8 per million to write to the cache once and $0.20 per million each time a request reads it again: 143 re-reads add $28.60. About $37 per million over its life, more than four times what writing it cost. Over their life, the results of looking around came to about 11% of all the cost of the sessions before the pack was installed (15% in headless ones).

Our benchmark never saw this. A run ends when its task is done, so nothing it added is read again. We added a column, carry: the tokens a run added to the context × 140 later requests × the cache-read price, beside the run's own cost (carry.py). With carry, a run costs roughly what the same task costs inside a session that goes on.

#Windows after a search

The first seek came from the same sessions. The most common predictable step after a search was opening a file it had just listed, mostly to read the lines around a hit. So seek attached them to the search's result: a narrow search got the lines around its hits (7 before, 30 after), a broad one its files ranked and the top file's lines, an empty one up to three wider searches.

  • seek 0.1 took only a plain grep. Opus's searches are rarely plain: about 100 of 110 sat behind a cd, in a chain or in a pipe. It fired in 1 of 36 runs.
  • seek 0.2 read the hits from any read-only command line's output. Now it fired, and saved requests: 4.9 → 4.5 per task in a fresh session (−7.9%). The cost went the other way: +2.1% [−1.4, +5.5] fresh; −4.5% [−7.4, −1.6] in a long session, where a saved request is dearer.
  • With carry: +6.3% [+1.4, +11.2] fresh, and −2.2% [−5.2, +0.7] in the long session, no longer shown. The windows saved requests by adding text, and the text outlived the requests it saved.

Replayed against what Claude actually did next in the mined sessions, a window held Claude's next read in 0.5 to 12% of searches, depending on its size. At every size, its tokens cost more over their life than the requests it saved. The windows are retired (note 5).

#An order in the middle of a search

The same sessions showed where the money sits: from the third consecutive request of looking around on, chains held 15% of requests and 10 to 16% of the cost, mostly in contexts over 400k tokens. pathfinder watched for exactly that, and at the third such request in a large context told Claude to hand the rest of the search to a cheaper read worker through delegate.

Its plumbing worked; Claude did not follow. In five trial runs it took the order 0 times (in four of them the search was already over). In the measured batch, in a long session that had read click's docs and tests but none of its source, the order came in 6 of 12 runs and Claude handed off once. Cost −3.4% [−11.3, +5.1], not shown. Into the graveyard.

The mod that left

Lab notes 12 · 18 Oct 2026 · written by Claude from this repository's data

lsp-plus answered Claude's search for a name in your code with the language server's answer: the exact places that use it, from the engine your editor uses. It made the cut in October, when renames on click took 3.4 requests with it instead of 4.6. In 0.7.0 it leaves the pack. This note is why: what its servers cost, how much of the code they actually saw, and two benchmarks that found the pack no more expensive without it.

#What a server costs

A language server is a process per language per session, running from the first question to the session's end. lsp-plus asked the first question itself, at session start, so each server would be warm when Claude needed it.

  • Memory. pyright on this lab's own repository took 3.5 GB: it read 57,201 Python files, nearly all of them in git-ignored checkouts, where git tracks 82. Told to skip the ignored folders, it took 237 MB. An empty project costs 90 to 130 MB per process, the TypeScript server up to 2 GB on a large repository, and every session starts its own.
  • Without lsp-plus, no server starts. Claude Code starts a server only when something asks it. In 24 runs where lsp-plus started none (12 without it, 12 with an engine that needs no server), not one diagnostic reached the conversation: no server had started.

#What its answers were worth

  • Who asked. In 1,931 benchmark runs with the pack, Claude called the language server itself 3 times; cells' refs() and defn() were called 0 times and rename() once in 482 cells. delegate looked up a hand-off's places 412 times in 195 hand-offs, the one real consumer, and it falls back to a text search without a server.
  • What the server saw. On real code the answer was often missing. On 30 SWE-bench issues in Django and sympy, lsp-plus recognised 55 searches for a code name in 25 runs and answered 6 of them, in 2. We took 128 names from 236 such searches in 29 checkouts. 49% have one definition, 30% several (a median of 5 namesakes), 20% none in the repository. For 49 names with one definition, the share of their uses in the code each engine found, and how many of its hits were real:
Engine Found Precise
pyright, the language server 50% 95%
Graphify, a code graph 49% 94%
Trail-Code, a code graph 47% 97%
A word search, each hit named by its enclosing function 100% 75%
The same search, hits sorted into definitions and uses by the files' outlines 98% 91%

The server missed half of the uses because Python here is untyped: self.query.get_compiler() names a method on a receiver whose type pyright cannot know. Classes fared worst (36% found), then methods (62%) and functions (68%). The two code graphs, built from the same kind of analysis, missed the same half. A plain word search finds every use and some namesakes, and the files' outlines sort most of the namesakes out in 87 ms, with no server.

#The diagnostics

A running server reports problems in the files it has open, and Claude Code adds those reports to the conversation after each tool's result. In one long lab session, 403 reached the conversation; 21% repeated one already sent, moved by a line after an edit; most were about files nobody had edited, from tests the benchmark keeps hidden or from another session's work. #What leaves, and what stays

  • Gone with it: the grep answer, the warm-up, the docs named in references, the check for docs that still name a removed function, and /refs.
  • Stays: delegate and cells use a language server wherever one is installed, and fall back to text search where none is. Nothing in the pack starts one any more.
  • The update. modpack 0.7.0 no longer installs lsp-plus. At its first start it removes lsp-plus@claude-modpack once and says so in one line; someone who installs it again on purpose keeps it. Its last released version, 0.4.2, is in the v0.6.1 tag.

#What this does not show

  • Small batches. 2 to 3 runs per task and arm; the intervals are wide. Two batches, 120 runs, point the same way, and neither shows lsp-plus saving anything.
  • Typed code at scale. The TypeScript tasks are a library and an app of modest size. On a large typed codebase a server sees more of the uses than it did in Django; we have not measured that.
  • What a person does. Benchmark prompts are complete specifications. A person who asks "who calls this?" many times a day in a typed codebase may get more from a server than these tasks show. The servers are still there for them, through Claude Code's own LSP plugins.

Asked to revise a guide to at most 700 words, Claude wrote it at 1,052 words, counted them, and wrote the whole guide again three times: 798, 757, 694. Every write of the whole text costs all of it in output, the dearest token, and stays in the conversation for every later request to read. draft, new in 0.8.0, came out of that run. This note is how it got its shape: a version that cut in place and cost more, a version that aimed low and dropped facts, the one that shipped, and where it does nothing.

#Rounds of rewrites

The run above is one of six on the guide in the twelve-task benchmark of note 12, with plain Claude Code and with the pack. All six went the same way:

The pack 1,036 → 812 → 710

The pack without lsp-plus 1,065 → 746 → 714

Every first draft ran about half over the limit, and every run wrote the whole guide 2 to 4 times, 17 writes in 6 runs. No pack mod touched it: none of them knew a limit had been set. In prose, output is a large share of the bill. Without draft, it was 32% of a run's cost at the median, 20 to 44% across the six writing tasks below.

#Cutting in place cost more

draft 0.1.0 put the person's setting beside a prompt that sets a word limit: plan each part's share, then cut in place with Edit rather than rewrite. After each write of a Markdown or text file it showed the file's words as wc -w counts them.

In the first trial run on the guide, the first draft came out at 985 words, and Claude cut it in place with edits, through cells. The run cost $0.95 and 20,090 output tokens. The same task without draft averaged $0.86 and 17,674 over four runs. An Edit repeats the text it replaces and writes its replacement, and a cut spread over a whole document touches most of it. Past a small overrun, one more write of the whole text is the cheaper way down.

#Aiming low dropped facts

draft 0.1.1 asked Claude to aim for three quarters of the limit. A write more than a tenth over now showed each section's target for one more write; a smaller overrun was trimmed with one Edit. On six writing tasks, 48 runs, it cost 14.2% less [−17.7, −10.5]. In 2 of 4 FAQ runs it also left out the escalation order, a fact the request asked for. Aiming that low made the answers too terse to hold everything.

draft 0.1.2 aims at about 85% and says to cut wording, not facts. 0.1.3 adds the one rule that let it into the pack: if the facts a request asks for cannot all fit, keep them, and say how far over the limit the text runs. A limit should not cost quality, and a text that needs more words may have them. The setting, as it reads beside a 700-word prompt:

The person's setting for writing to a length (700 words here): first drafts run long, often by a third, and every write of the whole text costs all of it again in output and stays in the conversation. So before writing, give each part its share of the words and aim for about 600, keeping every fact the request asks for: cut wording, not facts. If those facts cannot all fit, keep them and say how far over the limit it runs, rather than dropping any. Each write of the document then shows its words as wc -w counts them. If it is still well over, it shows each section's target: write it once more to those, in one step, rather than cutting it down in rounds; trim a small overrun with one Edit.

Clean prompts, real prompts

Lab notes 14 · 18 Oct 2026 · written by Claude from this repository's data

route asks a classifier about every prompt you send. When the answer is feature or test work, it tells Claude to hand the job to delegate's worker before reading the code (note 10). Until 0.8.1 that classifier had been measured on 25 prompts, each one clean and complete on its own, and both outside services got all of them right. This note covers three things. First, what happened when we tried to replace the outside service with a model small enough to run on your machine. Second, what the outside services do with real prompts. Third, what route is worth in a real session, which is less than the benchmark said.

#Why a local classifier

route sends the start of each prompt to a US service and needs that service's key. A model that runs locally would make route free and private, and could let it be on by default. A classifier for seven labels doesn't need a large model, so we built small ones: kilobytes in size, answering in microseconds.

#Clean prompts are easy

The first one was a 64 KB classifier (logistic regression over hashed word and letter n-grams). We trained it on 560 prompts that Haiku wrote for us, 80 per label, so that no real prompt was needed. It passed every clean test we gave it:

  • route's 25 prompts: it handed off exactly the 6 that route should, and labelled 23 of the 25 right.
  • 75 paraphrases of them: it found every feature and test prompt, and 64% of what it handed off was one.
  • 210 mid-session prompts, also written by Haiku: 196 right.
  • Trained on one generator's prompts and tested on another's: an AUC of 0.96.

#Real prompts are not

We then took 918 distinct real prompts from Claude Code sessions: the author's own and four public sets of Claude Code traces (CC-BY or MIT). Haiku labelled them by route's rubrics. On these prompts the AUC fell to 0.74. Of everything the classifier handed off, 59% was feature or test work. On the author's interactive prompts it was 18%: 83 of its 101 hand-offs were wrong.

Two things are behind that number:

  • Few real prompts are feature work. Of the author's 221 interactive prompts in the set Jev and ScaleDown saw, Haiku called 27 feature or test work. Across all 877, it was 398. The public sets hold many templated task prompts, and the author's sessions hold conversation.
  • A prompt in the middle of a session carries little on its own. "ok, build it like that" is feature work only with the conversation before it, and no classifier here sees that conversation.

Adding real labels from the other sources (training on all but one source, testing on the one left out) brought precision on the author's prompts to 21%, and no higher.

#What route is worth in a real session

The benchmark said −14% (note 7). That came from a mix of eight jobs in which the feature and the tests were the dearest. A real session has a different mix:

  • In the author's sessions, the turns Jev hands off were 13% of the spend.
  • In the benchmarks, a hand-off saved about a third to a half of a feature or test job (note 10). Applied to that 13%, it saves at most 4 to 7% of everything.
  • Counting the hand-offs that were not feature or test work, it is nearer 3 to 6%.

That is why route stays optional. It needs an outside classifier and its key, it sends the start of each prompt to a US service, and for the author it would save a few percent. The README, the installer, /modpack:setup and route's own setup now say all of that before you turn it on.   • One author. 221 interactive prompts in the real set, 27 of them feature or test work. A person who works differently may see different precision.
  • The 3 to 6% is a calculation from shares of spend and the benchmarks' savings, not a comparison in real sessions.
  • Context, not tested. A classifier that also read the end of Claude's last message might handle "ok, build it like that". Sent to an outside service, that is more of your text leaving your machine; run locally, it needs a model no mod can host yet.

Compaction in milliseconds

Lab notes 15 · 19 Oct 2026 · written by Claude from this repository's data

When a long session compacts, Claude Code stops, reads the whole conversation once more and writes a summary of it, and you wait while it writes. In this lab's own session at 436k tokens that wait was 102 s; in a test session at 67k, 15.2 s. smart-compact 0.3.0 writes its summary before it is needed, in the background as a turn ends, so the compaction itself only swaps it in. This note covers how that works, the bug that only a live session showed, what the summary written ahead cost and kept against /compact, and why we did not make the summary programmatic.

#Where the wait comes from

A compaction is one model request: the conversation in, a summary out. The input is mostly a cache read and costs little time; the summary is output, written token by token, several thousand of them. Nothing else in the session can happen meanwhile.

Claude Code already avoids that wait for its own automatic compaction. Since 2.1.301 it writes that summary well before the auto-compact point, and the compaction then takes about 40 ms and keeps every message since as it is. A mod cannot move that point per session; it is one window for every session. smart-compact compacts much earlier, after a turn, when the compaction pays back within a set number of requests (0.8.0), and there no summary is waiting.

#Writing it before it is needed

At a turn's end where a compaction after the turn is due, smart-compact asks a fork of the session for the summary, with its own six-point prompt. A fork reads the session's own cache, so the summary costs what Claude Code's would: repriced on a warm cache, the bench's summaries came to $0.13 on average ($0.09 to $0.24).

When the compaction comes, smart-compact's own compaction hook answers with the summary, then every message after the last one the fork read, as they are. Claude Code's engine never runs. If the conversation no longer matches what the fork read, the summary is dropped with one line saying why (counts and lengths only), and Claude Code summarizes as before.

#The bug only a live session showed

The first live try was in this lab's session, at 436k tokens. The fork wrote its summary in the background, and then the engine summarized anyway: 102 s. The debug log named the reason in one line: a re-entry, raised by smart-compact itself. A mod's own $.session.compact runs through every compaction hook but the calling mod's, so the hook holding the summary never saw the compaction it had asked for. The engine wrote a fresh summary while the one written ahead sat unused.

The 36 unit tests had passed. The test kit calls a mod's hooks directly; it has no notion of which mod raised an event. Two more things only showed up live:

  • A headless session cannot compact from a mod. claude -p answers $.session.compact with "not available in a headless session yet". The live checks ran in an interactive session in a detached terminal, with a debug log.
  • The first check never loaded smart-compact. It depends on statusline; with statusline off, Claude Code skips it with one line in the debug log and nothing in the session.

The fix asks through /compact, which Claude Code raises as a manual compaction that every hook sees, smart-compact's included. The transcript shows the summary as one line, whole under ctrl+o.

#Why not a summary without a model

Output is the dearest token, $20 per million on Opus 5.5. Could Claude instead write one cell that greps, filters and sorts the conversation into a summary, with no summary token written as output?

  • About a fifth of a summary is copying. In two of Claude Code's summaries from this lab's session (22,136 and 20,173 characters), 17% and 20% of the text repeats the conversation word for word. In 17 of the bench's summaries written ahead (8,535 characters on average) the share was 19%. The rest is judgement: what was decided, what was superseded, where the work stands. A search finds text; it does not decide what still matters.
  • In money, about $0.02. The session's summaries were about 5.5k tokens of output, about $0.11. Their copied fifth is about $0.02, roughly what the cell's own code would cost in output.
  • In time, nothing. Writing ahead already hides the time.

The other way to compact with no model is to drop the old tool calls and results and keep the rest. Before its last compaction, this lab's session held, in characters:

Tool results Tool calls Prompts Claude's text Thinking
46% 34% 12% 6% 2%

Keeping the prompts and Claude's text keeps 18% of the context; a summary keeps about 1%. Every kept token is read again by every later request, so the bigger context costs more to carry than the summary costs to write.

What a kept token costs over its life settles it. Per 1,000 tokens of summary on Opus 5.5: $0.020 written once as output, $0.008 written to the one-hour cache, then read again by a median of 143 later requests (note 11) at $0.0002 each, $0.029. About $0.057 over its life, and output is about a third of it. The lever is a shorter summary, not a cheaper way to write the same one. Claude Code's format re-types every message the person sent (about 3,000 characters in this session's) and pastes code that is already on disk. A leaner summary prompt is the next test; it has not run.

#Off until you turn it on

The summary written ahead comes with compaction after a turn (afterTurnPayback), and that is off by default. It stays off until it has run in more real sessions. Compacting after a turn is an investment: on short tasks that end right after it, it cost more (0.8.0). With it on, the summary written ahead removes the wait; it does not change when compacting pays.

#What this does not show

  • Few live runs. A handful of compactions, on Sonnet 5.5, at about 70k tokens. The 436k figure is the engine's own, before the fix.
  • Easy tasks. 18 runs per arm, on tasks both arms mostly solve. The bench can show what a summary loses on these tasks, not on longer work after the compaction.
  • The copied share comes from two of Claude Code's summaries in one session and 17 bench summaries. It is a measure of overlap with the conversation, not of what a program could have chosen.
  • The lean summary is a proposal, not a result.

What a system prompt can order

Lab notes 16 · 19 Oct 2026 · written by Claude from this repository's data

Every order this lab gave that Claude followed came beside the person's prompt (note 11). The one place we had not tried with care was the system prompt, which Claude reads before anything else, on every request. A mod can add sections to it, so we wrote one, steer, with two short sections: how to work toward the person's goal and what done means, and which steps pay with the pack's tools. Before a full benchmark we ran a smoke test. steer read the requests a little more closely, cost 9% more, and did not do either of the two things it asked for most plainly. It stays in the lab.

#The prompt Claude already has

Claude Code's own system prompt is lean, about 2.9k tokens; tool definitions and the skills list fill most of a session's fixed context. The pack already adds one section: cells' "Fewer round-trips", a paragraph and four lines on getting what you already know you need in one step, then a paragraph on when run_cell does it (guide.ts). Claude uses run_cell, so a system-prompt section is not always ignored. The question was whether a section could do more: make Claude read what the person is after, settle what done means, and reach for the pack's tools where they pay.

steer's two sections added about 680 tokens to a first request of about 26k. The first one asks for the method:

For a request to change something, settle what done means before you start: the few things the result must do or show, each one you can check. When the request leaves room for doubt, name them in a line before you act, so the person can correct them cheaply.

and, before finishing, to check each of them against what was observed and say in a line which hold. The second lists the steps that pay: looking around in few steps, edits and their check in one run_cell, fully specified work (a feature from a clear spec, tests to a target) through hand_off, long jobs in the background with track_progress, and a word limit met in one draft.

#What it changed

  • Longer answers. The five answers came to 1,039 words with the pack, 1,139 with steer and 1,222 without the prompt orders; output rose 16% and 38%.
  • A closer reading, once. On click.Duration, steer's answer checked its result against the request item by item, under "Checked against what you asked for", and listed choices the person might revisit: it had read "anything else fails" literally, so an integer is rejected rather than taken as seconds, and a test pins that down. The pack's answer to the same task listed two things it had added unasked. Without the prompt orders, the bug fix added a page-level test of what the user had reported and explained why the existing tests missed it (their users are admins); that run cost 64% more than the pack's.
  • Not what it asked for most plainly. No run named what done means before it started: 0 of 10 runs with steer. One checked its result at the end, the feature above. The feature is the work steer's hand-off line describes, and neither steer run handed it off, as no run in the batch did.
  • No more cells. run_cell came 4, 3 and 6 times. steer's line about it added nothing to what cells' own section already says.
  • The system prompt instead of the prompt cost the most. Without seek's order, steer's own line about looking around in few steps was the only guidance left; the runs added 80.5k tokens to the context instead of 56.5k and cost 20% more than with the orders on. The brief left out one of its required action items and scored 0.95.

#Why the system prompt loses

The system prompt shapes how Claude works: what it checks, what it reports, how it writes. What it does not do is outvote the judgement Claude makes at the moment it picks a step. cells' section works because it points where Claude already wants to go: fewer round trips are fewer steps for Claude too. Handing off asks Claude to give up control of work it can do. hand_off's own description says to keep lookups, small edits and what depends on the conversation in house (register.tsx), and no system-prompt sentence has moved Opus there (note 2: a routing rule in the system prompt, 14 runs, 0 hand-offs). Naming criteria before acting adds a step to a plan Claude already has. That is our reading; the counts are not:

#What we decided

The system prompt stays lean. steer stays in the lab, and the 108-run benchmark planned behind it was not run: it would have measured a cost of about 9% for a closer reading the grading cannot see, while the two orders steer gave most plainly were not followed. What a person wants said on every request belongs beside the prompt, in the person's name, the way seek and draft say it.

#What this does not show

  • Five tasks, one run each. That shows direction, not proof. With one run per task there is no range, and the +9% is not shown.
  • The grading cannot see intent. Hidden tests and term lists say whether a result is right, not whether it is what the person meant. Every arm got full marks on four of the five tasks. "A closer reading" is our reading of ten answers.
  • Complete specifications. Every bench prompt says exactly what it wants. Vague requests, where reading intent matters most, were not in this run. A smaller test of the first section alone on vague requests was planned and not run.
